오늘은 새 기능보다 런타임·평가 재현성의 경계 조건이 드러난 날이다. vLLM은 VLM 시간축과 multimodal embedding, ONNX 계열은 kernel·quantization·fixed-resolution VLM, 평가 하네스는 batch·cache·metric 일관성의 위험 신호가 나왔다.

## 1. vLLM

선정 이유: 2026-11-03~04 공식 tracker에서 서로 다른 multimodal 실행 경로의 위험 신호가 열렸다. 성능값은 이슈 작성자의 단일 H100 보고이며 공식 보장값이 아니다.

1. 정확한 이름: vLLM
2. 공식 위치: https://github.com/vllm-project/vllm
3. 종류: model serving / inference runtime
4. 기능: OpenAI-compatible API 등으로 LLM/VLM 추론을 서빙한다.
5. 해결 문제: GPU 추론 배치·서빙을 application code에서 분리한다.
6. 지원 client: Python 및 OpenAI-compatible HTTP client. Codex/Claude Code/Cursor 전용 plugin은 확인되지 않았다.
7. 설치: Python package 또는 container.
8. 오픈소스: 예.
9. 라이선스: Apache-2.0.
10. 실행 위치: local 또는 사용자가 배포한 cloud GPU.
11. account/API key: local serving에는 필수 계정 없음; model hub/remote endpoint는 별도 인증 가능.
12. read 권한: model weight·config·입력 image/video.
13. write 권한: cache·log·download path.
14. shell/browser/Git/filesystem/network: shell·network·filesystem 사용; browser/Git 직접 제어는 확인되지 않음.
15. security/privacy: image/video prompt endpoint 노출, request log, model 공급망 위험.
16. 최근 update 날짜: 2026-11-03~04 issue signal.
17. 최근 변화: #65523은 균일 32-frame index가 실제 video time 대신 00:00~00:30으로 표기된다는 보고, #65531은 enable_mm_embeds와 CUDA graph 조합 engine 종료 보고, #65513은 media-span attention routing TTFT 병목 보고다. #65513의 66개 32-frame clip/H100 390.3초→65.3초 값은 작성자 prototype 주장이다.
18. 개발 활동성: 여러 VLM runtime 경로의 최신 tracker 활동.
19. issue/PR 상태: 모두 open report이며 해결 완료가 아니다.
20. 문서 품질: 설치·서빙 API 문서는 있으나 timestamp 보장은 확인하지 못했다.
21. 코드/test 상태: 재현 조건은 있으나 main 전체 검증은 확인되지 않았다.
22. 무료/유료: 무료 오픈소스; GPU/cloud 비용 별도.
23. 장점: VLM prompt를 API로 빠르게 반복한다.
24. 단점: preprocessor·graph capture·frame sampling 디버깅 비용이 크다.
25. CV/AI 연구 적합성: 높음. video QA는 answer뿐 아니라 timestamp·frame·TTFT를 artifact로 남겨야 한다.

사실/저자 주장/추론: 이슈 조건·open 상태는 사실, H100 수치는 저자 주장, 시간축 regression 추가는 본 보고서의 추론이다.

## 2. ONNX Runtime GenAI

선정 이유: local VLM packaging에 직접 관련된 fixed-resolution VLM, quantization, cache PR이 최근 열렸다. 모두 병합 전이다.

1. 정확한 이름: ONNX Runtime GenAI
2. 공식 위치: https://github.com/microsoft/onnxruntime-genai
3. 종류: model builder / generative inference runtime
4. 기능: ONNX Runtime 위에서 생성 model 변환·패키징·추론을 지원한다.
5. 해결 문제: provider용 build와 local/edge 배포를 줄인다.
6. 지원 client: Python, C/C++/C#, JavaScript bindings; agent client 전용 통합은 확인되지 않았다.
7. 설치: 언어별 package와 model-builder workflow.
8. 오픈소스: 예.
9. 라이선스: MIT.
10. 실행 위치: local/edge 또는 user-managed cloud.
11. account/API key: local inference에는 불필요; model download는 인증 가능.
12. read 권한: ONNX graph·tokenizer·weight·build config.
13. write 권한: export/build package·quantized model·cache/log.
14. shell/browser/Git/filesystem/network: shell·filesystem, model 획득 시 network; browser/Git 직접 권한은 확인되지 않음.
15. security/privacy: 외부 model artifact/tokenizer 실행이므로 revision pin·checksum 필요.
16. 최근 update 날짜: 2026-11-02~03 open PR.
17. 최근 변화: #2841 fixed-resolution VLM용 llava model type, #2853 INT4/INT8 per-channel MatMulNBits, #2846 LongRoPE cache consistency 수정 제안.
18. 개발 활동성: 72시간 안에 VLM·quantization·cache 병렬 PR.
19. issue/PR 상태: #2841/#2846/#2853은 open PR.
20. 문서 품질: builder·quantization 문서는 있으나 PR 호환 범위는 병합 후 재확인 필요.
21. 코드/test 상태: PR별 CI/benchmark 최종 결과는 확인되지 않았다.
22. 무료/유료: 무료 오픈소스; hardware/storage 비용 별도.
23. 장점: VLM을 ONNX/quantized artifact로 묶어 device 비교 가능.
24. 단점: builder/EP/model 호환 매트릭스가 넓다.
25. CV/AI 연구 적합성: 중상. image-VLM quantization ablation에는 좋고 안정 배포에는 검증 부담이 있다.

사실/저자 주장/추론: PR 제목·open 상태는 사실, 지원·성능은 제안 단계, edge ablation 후보 평가는 추론이다.

## 4. ONNX Runtime

선정 이유: deployment graph에는 session 생성 성공 외에 numerical regression gate가 필요하다는 CUDA/CPU 이슈가 최근 열렸다.

1. 정확한 이름: ONNX Runtime
2. 공식 위치: https://github.com/microsoft/onnxruntime
3. 종류: inference runtime
4. 기능: ONNX graph를 CPU/GPU/여러 execution provider에서 실행.
5. 해결 문제: 연구 모델을 framework-independent graph runtime으로 배포·최적화.
6. 지원 client: Python, C/C++, C#, Java, JavaScript; agent client 전용 통합은 확인되지 않았다.
7. 설치: 언어별 package 또는 native build.
8. 오픈소스: 예.
9. 라이선스: MIT.
10. 실행 위치: local, edge, server/cloud.
11. account/API key: 기본 runtime에는 불필요.
12. read 권한: ONNX model·external data·provider config·input tensor.
13. write 권한: profiling·cache·build artifact/application output.
14. shell/browser/Git/filesystem/network: shell/filesystem, download/remote service 시 network; browser/Git 직접 제어 없음.
15. security/privacy: untrusted model/extension·device kernel·profiling log를 분리.
16. 최근 update 날짜: 2026-11-03~04 issue 목록.
17. 최근 변화: #33863 CUDA MoE gated GELU wrong result, #33864 CUDA MoE slowdown, #33866 CPU MoE chained I/O wrong result, #33874 Pad BF16 kernel 부재 보고.
18. 개발 활동성: CPU/CUDA/WebGPU/operator 경로의 동시 tracker 활동.
19. issue/PR 상태: 모두 open issue이며 제목만으로 bug 확정은 아니다.
20. 문서 품질: provider/package/release 문서는 넓으나 edge case는 tracker 추적 필요.
21. 코드/test 상태: 수치·성능 regression 가능성 보고; 전체 CI는 확인되지 않았다.
22. 무료/유료: 무료 오픈소스; GPU/cloud 비용 별도.
23. 장점: 동일 artifact provider별 비교에 적합.
24. 단점: operator·dtype·provider 조합별 차이.
25. CV/AI 연구 적합성: 높음. PyTorch 기준 cosine/max error와 latency를 동시에 gate할 때 좋다.

사실/저자 주장/추론: 이슈 제목·open 상태는 사실, 회귀는 작성자 보고, numerical gate 필요성은 추론이다.

## 오늘 바로 설치/시험할 Top 3

1. vLLM: 30초·150초 synthetic clip 두 개를 동일 32-frame 설정으로 넣어 timestamp·frame index·실제 FPS를 CSV 비교한다. 통과 기준은 timestamp error 1 frame 이하 또는 해당 경로가 timestamp를 보장하지 않는다는 명시 결론이다.
2. lm-evaluation-harness: 고정 sample 20개를 batch 1/4/8로 실행해 effective batch·prompt token·result JSON hash를 저장한다. 설정과 log가 불일치하면 score 비교를 중단한다.
3. ONNX Runtime GenAI: 작은 fixed-resolution image encoder를 FP16/INT8로 한 번씩 export해 build time·peak VRAM·p50 latency·embedding cosine을 비교한다. 사전 cosine threshold 미달이면 open-PR 경로를 중단한다.

## CV/AI 연구·코딩 workflow에 특히 유용한 것

- PyTorch repo에서 ONNX Runtime/ORT GenAI export 뒤 PyTorch 기준 output, preprocessing, provider별 latency를 동일 artifact로 저장한다.
- vLLM video reproduction에는 frame index, sampling policy, FPS, timestamp prompt, response를 함께 versioning한다.
- lm-evaluation-harness에는 config hash·backend version·effective batch를 별도 manifest에 보존한다.
- DeepEval은 VLM 설명문/agent research assistant schema regression에는 유용하나 cache를 독립 run directory로 격리한다.

## 오늘은 굳이 설치하지 않아도 되는 것

- DeepEval: agent evaluation이 현재 병목이 아니면 cache-key 이슈가 merge·test로 닫힐 때까지 보류한다.
- ONNX Runtime GenAI: 최신 LLaVA/quantization PR은 production이 아닌 isolated build 실험용으로만 취급한다.
- ONNX Runtime: PyTorch만으로 충분하고 export 목적이 없다면 provider 경로 추가 비용이 이득보다 클 수 있다.
- 전날 agent framework: 새 release/security change 없이 반복 설치하지 않는다.

### 오늘의 패턴

핵심은 도구 수가 아니라 설정값·입력 변환·cache key를 결과와 분리하지 않는 것이다. multimodal에서는 frame sampling, runtime에서는 kernel/provider, 평가는 batch·rubric·schema가 숨은 독립변수다. 다음 보고서에서는 실제 merge/release가 나온 도구만 재평가한다.
