| 24. 단점 | 토큰 권한이 넓으면 쓰기 피해 반경이 큼; 오늘 신호가 미릴리스 main이라 즉시 프로덕션 고정에 부적합 |
| 25. CV/AI 워크플로 적합성 | 논문 코드의 이슈·PR·Actions·대형 로그/파일 탐색을 자동화하는 데 높음 |

- **확인된 사실:** 세 커밋은 main에 존재하고 최신 정식 릴리스 v2.0.2보다 새롭다.
- **작성자 주장:** 공식 문서는 원격/로컬 설치와 toolset/read-only 범위 축소를 지원한다고 설명한다.
- **해석:** 대용량 파일을 resource link로 바꾸는 것은 모델 문맥과 전송 비용을 낮추지만 클라이언트의 resource 처리 호환성이 새 실패 지점이 된다.
- **전망:** 다음 릴리스 전에는 기능 플래그나 커밋 고정으로만 시험하는 편이 합리적이다.
- **진단→가설→최소 실험:** 대형 로그/모델 메타데이터 파일이 MCP 응답을 과도하게 키우는지 진단한다 → resource link가 문맥 크기를 줄이면서 접근성을 유지할 것이라 가정한다 → 테스트 저장소에서 0.5MB/1.1MB 파일, UTF-8 경로, 150개 label을 읽어 1.1MB만 resource link, 모든 UTF-8 경로 정상, label 누락 0, 쓰기 호출 0건을 기준으로 둔다.

## 생태계 패턴과 결론

오늘의 공통점은 “더 많은 도구 호출”보다 **근거 보존, 결과 크기 제어, 비용·파괴성 설명, 실패 시 닫히는 기본값**으로 이동한다는 점이다. 코드베이스 메모리 도구는 성능 홍보보다 인용 정확도·비밀정보 처리·장기 세션 회귀를 측정해야 한다. 운영 MCP는 기능 수보다 권한 축소와 오류 의미가 더 중요하다. 따라서 오늘의 최소 행동은 새 도구를 전부 상시 연결하는 것이 아니라, 동일한 작은 저장소와 고정 질문·고정 실패 사례에서 Graphicle과 codebase-memory-mcp를 순차 A/B하고 protect-destructive의 오탐·미탐을 수치화하는 것이다.
